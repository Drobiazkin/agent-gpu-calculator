GPU / RAM Calculator for Agent Sessions — v27

The offload switch picks the mode: with OffloadingConnector (KV write-through to RAM) or resident (all sessions hold VRAM). vLLM has no TTL — both pools are managed by capacity + LRU, so “staleness rate” is computed here (capacity / inflow), and the RAM pool size is the knob, which becomes a fourth concurrency limit alongside VRAM slots, the PCIe bus and prefill-compute. Context is entered as the full value; the unique part = context − shared prefix, subtracted automatically.

This always holds the current scenario in full — copy it to share or save into a task. On the way back in, it accepts either a full link or just the one line after the hash sign.

Time per GPU step (t_slot)
—
Offload: swap-in + delta prefill + generation. Resident mode: delta prefill + generation. Plus, in both modes — the amortized initial task prefill (uniq_start/S). This is how long a session occupies a VRAM slot for one step.
Swap-in over PCIe
—
Loading the session’s entire KV from RAM into VRAM. The worst case is confirmed by the KV lifetime in VRAM: if it’s shorter than the tool wait, the blocks are already evicted by the time it returns.
PCIe load
—
Actual traffic of all sessions: from RAM — the full KV per step (dominant), into RAM — only new bytes (delta + initial prefills). Directions are summed against one direction’s bandwidth — conservative, since the bus is duplex.
Oversubscription
—
N / M. In resident mode ≤ 1.0× (the prefill flow can keep N below M too); you can’t fit more than M sessions per GPU without offload or recompute.
Prefill ceiling at this context
—
The GPU’s peak × MFU, divided by the work of one token: 2 · active parameters + 2 · full-attention layers · hidden_size · context length · f. The second term grows with context — so the ceiling DROPS as the prompt gets longer, and you can’t set one number for all lengths.
Miss = recompute
—
The cost of losing KV: re-prefill of the unique part + the delta (the prefix stays cached — all sessions keep it hot). It eats into the GPU’s overall prefill-compute, not just the slot.
KV lifetime in VRAM
—
LRU: free VRAM / inflow (loads + computed blocks). Shorter than the tool wait — the blocks are evicted from the GPU by the time it returns, so swap-in is full (built into the model). Longer — GPU hits dominate, offload is barely loaded.
KV lifetime in the RAM pool
—
RAM pool / inflow of new bytes (step delta + initial prefills). A live session refreshes the LRU position of all its blocks every cycle, so this must be ≥ the cycle; the survival guarantee is pool ≥ the working set N·KV, which is already accounted for by the N limit.

Estimate: mixed load

Mixed load is computed by SUMMING classes, not by averaging their parameters. This isn’t a simplification but an exact result: as long as the classes are bound by the same resource, the replica’s total capacity equals the weighted sum of the demands, and a separate calculation gives exactly the same number. Averaging the inputs instead (one “average” context, one “average” wait) is off by up to 70%, because per-agent demand is nonlinear in these fields. Workflow: pick a class, set its number of agents, press “+ add to estimate”, repeat for the next one.

The decode batch is self-consistent: only sessions in the generation phase read KV (b = X·t_gen, an iteration), not all residents — the previous assumption “the batch is always full” underestimated procurement when bound by prefill. Built in conservatively: a full KV reload on every step, both PCIe directions counted against one direction’s bandwidth, prefill double-counted in both slot occupancy and the overall ceiling, K copies of the prefix in both pools. Prefill↔decode interference is NOT accounted for (prefill chunks steal bandwidth from generation) — the only safeguard is the allowed utilization < 100%. Failure reserve is the “+1 node” checkbox (included in the procurement header).

How this is computed — model description

The question the program answers: how many GPUs and how much RAM are needed to hold a target number of live agent sessions on on-prem vLLM. A live session is a harness-level metric: an agent cycle in flight, including the tool-wait phase. A vLLM request exists only during the active part of the step; physically, at most M sessions are on the GPU at once, the rest are blocks in the CPU pool at that moment. If the business target is given in steps/day rather than live agents, recompute: live agents ≈ (steps/day ÷ 86,400) × cycle duration T — a faster decode makes the cycle shorter, so fewer live agents are needed for the same work.

Context semantics. The full session context and the shared prefix are entered; the unique part = context − prefix, subtracted automatically. The prefix is the byte-identical head of the prompt across all sessions in the batch: APC stores its KV in VRAM once, LRU touches from all sessions keep it hot, it is not swapped and not re-prefilled. The unique part is what scales with the number of sessions: only it occupies slots, travels over PCIe, and lives in the RAM pool.

Step lifecycle in vLLM terms. A request is prefilled and decoded up to the tool call, then completes; its blocks stay in the GPU prefix cache. While the tool runs, the request doesn’t exist — the session lives in the harness, and with OffloadingConnector enabled its blocks are write-through copied into the CPU pool. The new request with the tool result appended finds the longest cached prefix, and there are three outcomes: a GPU hit (blocks not evicted — only delta prefill), a RAM hit (loading the unique part over PCIe + delta prefill), a miss (re-prefill of the unique part; the shared prefix is kept in cache by the other sessions).

Formula chain. KV: kv_u = uniq · KiB/token, kv_s = prefix · KiB/token. Slots: M = ⌊(TP·VRAM − weights − K·kv_s) / kv_u⌋, where K is the number of DIFFERENT prefixes coexisting on the replica (each stored as a copy). Decode (memory-bound): t_tok = (weights + f·b·(kv_s + kv_u)) · 1.074 / (TP·HBM), where b is the SELF-CONSISTENT decode batch: b = X·t_gen, solved by iteration, because only sessions in the generation phase read KV, not all slot residents (a full batch M when bound by prefill UNDERESTIMATED procurement: slower decode lengthened the cycle and inflated N per replica); 1.074 converts GiB to decimal GB; f is the fraction of KV read by attention (1.0 for dense/GQA/MLA; lower for sparse — GLM-5.2 DSA, V4 Flash CSA/HCA; storage and swap are always full). Every decoding session reads the shared prefix — cascade deduplication is deliberately not built in, see “Modes”. Weight bytes are read in full: MoE touches almost all experts at a full batch, “active parameters” only apply in prefill. MTP/speculative decoding is given as a multiplier (accepted tokens per pass, already net of rejected ones): t_gen = out · t_tok / MTP, the SLA read budget is multiplied by MTP; prefill and the KV/PCIe/RAM volumes don’t change. GPU step: t_slot = swap_in (kv_u/PCIe) + delta prefill (at the append-token price) + amortized initial task prefill (uniq_start/S at the from-scratch price) + t_gen; the full cycle T = t_slot + tool wait. Step throughput X is the minimum of three ceilings: slots min(M_mem/t_slot, M_sla/t_gen) — VRAM holds M_mem residents, SLA only caps decoding ones; PCIe / bytes per step (loading kv_u + writing new blocks + amortized start kv_u/S); the replica’s prefill ceiling (GPU tok/s × TP) / tokens per step (delta + uniq/S + m·uniq, where m is the cache-miss fraction: every miss = re-prefill of the unique part) — prefill is a shared compute resource, not a per-slot one. The prefill and PCIe ceilings are multiplied by the target utilization ρ: sizing at 100% is the point of unbounded queue growth, headroom is mandatory. Each input feeds exactly one phase: prefill tok/s — only the prefill terms (t_pref, the flow ceiling, the recompute cost); f — only decode reads (t_tok, the SLA budget); PCIe — only swap; there are no formula links between them, sparse attention enters decode explicitly through f, and enters prefill implicitly, inside the entered tok/s. Concurrency via Little’s law: N = X · T, with a fourth limit N ≤ (replica pool − K·kv_s)/(kv_u · headroom), where the replica pool = node RAM ÷ replicas-per-node, and headroom is a configurable multiplier (in-flight completed tasks, start bursts, tail blocks). The actual flow Xserv = N/T feeds every derived metric (PCIe utilization, tok/s, inflows). RAM per replica = N · kv_u · headroom + K·kv_s — this is the cpu_bytes_to_use value; RAM procurement is counted in nodes. Replicas = max(⌈target / ⌊capacity⌋⌉, ⌈required step flow / X_max⌉) — memory (“how much fits”) and throughput (“how much it delivers”) are TWO independent procurement conditions, the larger one binds; capacity is taken as a WHOLE number (a fractional one hid a deficit of up to 1–2% when the target is a multiple of a near-whole capacity), and X_max comes from the self-consistent unbounded equilibrium under actual swap, or from the resident ceiling without it, so it doesn’t depend on the RAM pool size. GPU = replicas × TP; at TP > 1 the weights, prefix and KV are sharded across the replica’s GPUs, and their HBM and PCIe add up (ideal scaling, allreduce overhead not accounted for). If an SLA tok/s is set, the decoding batch is capped by inverting the SAME pass equation used to compute speed (both roofline branches — reads and compute, accounting for compute occupied by prefill); the cut is continuous, capacity rounding happens only at the output. SLA is a lower bound: a batch that’s small for other reasons gives speed ABOVE SLA. N = max(resident capacity, min(flow, RAM pool)) — an empty CPU pool doesn’t push N below resident mode (see “Modes”); when the flow doesn’t feed residents, free VRAM stays available for waiting sessions’ blocks.

Nodes and TP limits. Tensor parallel lives inside an NVLink/NVSwitch domain (HGX H100/H200 = 8 GPUs, NVL72 = 72). Cross-node TP is technically possible (NCCL over IB/RoCE), but 2·L allreduce per token over the network cuts decode by 30–50% with per-card efficiency dropping roughly by half — this strategy is dominated by TP=domain × PP (one activation transfer at the stage boundary instead of 2·L allreduce) or EP for MoE; the model doesn’t account for them, so TP > domain is flagged as outside the model. Procurement is done in whole nodes: replicas per node = ⌊node/TP⌋, nodes = ⌈replicas / replicas-per-node⌉; a TP that doesn’t divide the node evenly leaves idle GPUs — they’re shown separately. GPU(TP) is non-monotonic: the replica pool = TP·VRAM − weights — a difference near the fit threshold, where the added GPU goes entirely into the pool and multiplies M; the calculator does NOT sweep neighboring TP values — it warns near the fit threshold, so check the minimum GPU count manually at TP±1. Beyond the domain, scaling is by replicas through load balancing, mandatorily sticky per session; EP and PP over the network aren’t accounted for by the model.

Cache staleness. vLLM has no TTL: both pools are managed by capacity + LRU, so block lifetime is computed as capacity / inflow of new bytes. In VRAM the inflow = loads + computed blocks; in RAM — only new bytes (delta + task starts), hits refresh LRU without writing. If the VRAM lifetime is shorter than the tool wait — the blocks are already evicted by the time it returns, so swap-in is treated as full. The survival guarantee in RAM is the working-set limit (N · kv_u must fit in the pool), which is already built into N.

Modes. Offload off — resident mode: N = resident capacity (min of M and the prefill flow), PCIe and the RAM pool aren’t used, every session holds VRAM through the tool wait. Resident capacity also serves as the FLOOR of offload mode: an empty CPU pool doesn’t push N below it — vLLM doesn’t evict GPU blocks for the sake of an empty pool, offload only adds on top. When there’s no actual swap (the pool adds nothing beyond resident capacity, or N ≤ M), procurement and the flow ceiling are also computed along the resident line — turning the offload checkbox on can’t make the numbers worse than off. Cascade attention (reading the shared prefix once for the whole decode batch) is NOT built into the model — the conservative case “each session reads the prefix on its own” is always assumed. Reason: in vLLM V1 the cascade is enabled by a fragile heuristic (prefix ≥ 256 tokens, ≥ 8 requests, a perf check) and requires a SINGLE prefix across the whole batch — a multi-agent mix of manifests on a replica breaks the condition, and with a short prefix its contribution is < 1% of decode time. If the cascade actually kicks in on the test bench — that’s extra speed headroom beyond the calculation (at a ~30k-token prefix — up to ~20% of decode). The recompute variant (eviction without offload) is shown for reference in the bottom row of the cluster block.

How to get the read fraction f. A priori: for select-at-read architectures (DSA — the full KV is stored, selection happens at read time) f(L) ≈ (top_k + window)/L + b_indexer/b_kv; top_k and window are in config.json and the model’s tech report; f drops as context grows and has a floor due to the indexer scan. For compressed-storage (V4 Flash CSA/HCA) the compression is already baked into KiB/token and most of what’s stored gets read — f is closer to 1; models are fairly compared by the product KiB/token × f, since that’s what actually eats bandwidth. A posteriori (the decisive method, which also calibrates effective HBM): two measurements at a full batch with MTP off — a short context gives bandwidth BW = weights / (TP · t_tok), a long one gives f = (t_tok · TP · BW − weights) / (M · kv_session).

Conservatism and test-bench verification. Built in: a full reload on every step, both PCIe directions counted against one direction’s bandwidth, prefill counted twice — into both slot occupancy and the overall ceiling. Measure on the test bench: prefill tok/s (vllm bench serve), the effective PCIe DMA bandwidth, whether cascade attention actually kicks in (not built into the calculation — its actual occurrence gives extra decode speed headroom). Check on your vLLM version whether blocks formed DURING DECODE get offloaded (issue #33864: in some versions such blocks didn’t make it into the CPU pool — on return, the tail of output tokens went into re-prefill). CPU pool size is set by cpu_bytes_to_use (bytes per instance, split across TP workers; num_cpu_blocks in older versions). Check max_num_seqs and max_num_batched_tokens: the vLLM scheduler can cap the batch before memory does — the model doesn’t know about this ceiling (an indirect signal is the warning about degraded per-session speed). Real numbers are usually 10–30% better than the calculated ones.
